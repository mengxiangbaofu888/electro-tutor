# 开发与部署步骤

## 一、环境要求

| 用途 | 需要 | 本项目实测版本 |
|---|---|---|
| 开发 / 构建网页版 | Node.js ≥ 22.13（pdfjs-dist v6 的要求） | Node 24.15.0 |
| 包管理 | npm（或 pnpm） | npm 11.x |
| 打安卓 APK | **JDK 21**、Android SDK（platform 36 + build-tools 36） | JDK 21.0.12 / Gradle 8.14.3 / AGP 8.13 |

> 💡 只想用网页版的话，**不需要** Java 和 Android SDK。

> ⚠️ **必须是 JDK 21**。Capacitor 8 的安卓模板要求 `sourceCompatibility JavaVersion.VERSION_21`，用 JDK 17 会直接构建失败。

---

## 二、本地开发

```bash
npm install
npm run dev
```

会启动 Vite 开发服务器（默认 http://localhost:5173）。

### 在手机上调试
1. 手机和电脑连同一个 WiFi；
2. 看终端里的 `Network` 地址（形如 `http://192.168.1.10:5173`）；
3. 手机浏览器打开它 → 浏览器菜单里选「添加到主屏幕」。

这样就跟装了 App 差不多（全屏、有图标、离线可打开）。

### 常用命令

| 命令 | 作用 |
|---|---|
| `npm run dev` | 开发服务器（热更新） |
| `npm run typecheck` | TypeScript 类型检查（src + 构建配置两个工程） |
| `npm test` | 跑单元测试（433 个用例，含交互测试、文档一致性检查与完整闭环集成测试） |
| `npm run test:watch` | 单元测试监听模式 |
| `npm run probe:cors` | 探测各家大模型接口是否允许浏览器直连（不需要 API Key） |
| `npm run build` | 类型检查 + 生产构建到 `dist/` |
| `npm run build:fast` | 跳过类型检查直接构建（应急用） |
| `npm run build:single` | 生成单文件离线版 `dist-single/single.html` |
| `npm run build:preview` | 生成**可离线打开**的 UI 预览产物 `dist-preview/preview-*.html` |
| `npm run serve` | 用内置极简服务器预览 `dist/`（默认 4173 端口） |
| `npm run cap:sync` | 构建网页产物并同步进安卓工程 |
| `npm run apk` | 一键构建调试版 APK（需 JDK 21 + Android SDK） |
| `npm run apk:release` | 构建正式版 APK（需先配签名） |
| `npm run preview` | 用 Vite 预览构建产物 |
| `npm run icons` | 重新生成 PWA 图标 + 安卓图标/启动页 |

## 二点五、怎么看界面长什么样（视觉检查）

单元测试只能证明"DOM 里有没有某个元素"，证明不了"它看起来对不对"。
如果需要亲眼确认界面，用预览产物：

```bash
npm run build:preview
```

会在 `dist-preview/` 下生成 9 个**自包含的单文件 HTML**（首页 / 材料 / 大纲 /
掌握度 / 练习 / **答题页** / 错题本 / 学习报告 / 我的）。**双击就能打开**——不需要服务器、
不经过任何网络代理。

它是怎么做到的：预览入口（`src/preview.tsx`）会先注入内存版 IndexedDB
（`fake-indexeddb`）并塞一批示例数据，再加载应用主体。所以：

- 正式构建（`index.html` → `src/main.tsx`）**完全不受影响**，示例数据不会进 App；
- 预览产物里跑的是真实界面和真实业务逻辑，只是数据源换成了内存。

> 为什么要专门做这个：用 `file://` 打开正式产物时，浏览器不允许使用本地数据库，
> 页面会一直停在"加载中"，看不到任何界面。

README 里那几张界面截图（`docs/screenshots/`）就是用这些预览产物截的：
上面那条命令跑完，把 `preview-*.html` 在**手机宽度（800px 左右）**下截图即可。
它是**构建产物**，不进版本库（`dist-preview/` 已 gitignore），只用来人工肉眼确认。

## 三、部署网页版

`npm run build` 之后，`dist/` 是**纯静态文件**，扔到哪都能跑：

- **GitHub Pages**：把 `dist/` 推到 `gh-pages` 分支；
- **Vercel / Netlify**：构建命令 `npm run build`，发布目录 `dist`；
- **自己的 NAS / 服务器**：用 nginx 之类托管 `dist/`，注意 SPA 需要把所有路径回退到 `index.html`。

> ⚠️ 本项目用的是 `HashRouter`（地址里带 `#`），所以**不需要**配置服务端回退，放静态托管最省事。

## 四、打包安卓 APK

Capacitor 已经把 `dist/` 包进安卓壳，**`android/` 工程目录已经生成好了**。你要做的只是准备好工具链，然后一条命令出包。

### 4.1 准备工具链（只需一次）

| 组件 | 版本要求 | 说明 |
|---|---|---|
| JDK | **21** | Capacitor 8 要求；用 JDK 17 会构建失败 |
| Android SDK Platform | `android-36` | compileSdk = 36 |
| Android SDK Build-Tools | `36.0.0` | |
| Android SDK Platform-Tools | 最新 | 可选，用来 `adb` 装包 |

**装法一（推荐）**：装 [Android Studio](https://developer.android.com/studio)，它会顺手装好 JDK 和 SDK。

**装法二（只要命令行）**：

```bash
# 1) 装 JDK 21（Eclipse Temurin）
#    https://adoptium.net/temurin/releases/?version=21
# 2) 装 cmdline-tools，然后用 sdkmanager 装组件
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
```

设置环境变量并验证：

```
JAVA_HOME=<JDK 21 路径>
ANDROID_HOME=<Android SDK 路径>
PATH=%PATH%;%ANDROID_HOME%\platform-tools
```

```bash
java -version    # 必须显示 21.x
adb version      # 可选
```

> 💡 项目还支持一种"免安装"约定：把 JDK 和 SDK 放到**仓库同级的 `.android-tools/`** 目录里
> （`jdk-21/` 与 `android-sdk/`），`npm run apk` 会自动找到它们，不用配环境变量。
>
> 没有 Android Studio、或者网络受限装不上 SDK 时，仓库里有现成脚本：
>
> ```bash
> node scripts/setup-android-toolchain.mjs
> ```
>
> 它会自动下载 JDK 21、cmdline-tools、platform-tools、platform-36、build-tools 36.0.0，
> 解压并铺成标准 SDK 目录结构（含许可证文件），全程只依赖 Node，不写系统目录。

### 4.2 出包

```bash
npm run apk            # 调试版，产物在 android/app/build/outputs/apk/debug/
npm run apk:release    # 正式版，需要先配好签名
```

脚本会自动：① 类型检查 → ② 构建网页产物 → ③ `cap sync` 同步进安卓工程 → ④ Gradle 打包 → ⑤ 打印产物路径和 adb 安装命令。

> ⚠️ ① ② 不能省。只做 `cap sync` 的话，会把**上一次的 dist** 打进 APK——
> 明明改了前端代码却打出一个旧包，而且不会有任何提示。
> 所以如果你想手工出包，顺序必须是 `npm run build:fast` → `npx cap sync android` → `gradlew assembleDebug`。

也可以手工来：

```bash
npm run build:fast
npx cap sync android
cd android && ./gradlew assembleDebug      # Windows 用 gradlew.bat assembleDebug
```

### 4.3 装到手机

```bash
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

或者把 APK 拷到手机上点击安装（首次需要允许"安装未知来源应用"）。

### 4.4 关于体积

包内含 `pdfjs`（约 1.3 MB）与 React（约 0.7 MB），APK 通常在 5~10 MB。

### 4.5 排障

<details>
<summary><b><code>sdkmanager</code> 报 "Failed to download any source lists" / "IO exception while downloading manifest"</b></summary>

某些网络环境下 `sdkmanager` 拉不到 Google 的仓库清单。绕开办法是**直接下载组件压缩包，手工铺成 SDK 目录结构**：

```
<SDK>/
├─ cmdline-tools/latest/     ← commandlinetools-win-*.zip 解压后，把内层 cmdline-tools/* 放进来
├─ platform-tools/           ← platform-tools-latest-windows.zip（内层就叫 platform-tools）
├─ platforms/android-36/     ← platform-36_r01.zip（内层就叫 android-36）
├─ build-tools/36.0.0/       ← build-tools_r36_windows.zip（内层叫 android-16，**必须改名成 36.0.0**）
└─ licenses/
   ├─ android-sdk-license
   └─ android-sdk-preview-license
```

`licenses/android-sdk-license` 写入这三行：

```
8933bad161af4178b1185d1a37fbf41ea5269c55
d56f5187479451eabf01fb78af6dfcb131a6481e
24333f8a63b6825ea9c5514f83c2829b004d1fee
```

`licenses/android-sdk-preview-license` 写入：`84831b9409646a918e30573bab4c9c91346d8abd`

铺好后用 `sdkmanager --list_installed` 验证能否识别到这三个包。

国内镜像：把 `https://dl.google.com/android/repository/` 换成
`https://mirrors.cloud.tencent.com/AndroidSDK/`（文件名相同）。
</details>

<details>
<summary><b>App 里请求一直失败，网页版却正常</b></summary>

先看接口地址是不是 `http://`。安卓 9（API 28）起默认禁止明文 HTTP，
而 `AndroidManifest.xml` 里已经加了 `android:usesCleartextTraffic="true"` 来放行——
如果你自己改过清单或重新执行了 `npx cap add android`，这个属性可能会丢，检查一下。

另外：`npx cap sync` 不会覆盖你的清单文件，但 `cap add android` 会重新生成，注意别把改动弄丢。
</details>

<details>
<summary><b>Gradle 报 <code>Could not determine java version</code> 或 <code>Unsupported class file major version</code></b></summary>

JDK 版本不对。Capacitor 8 的模板写死了 `sourceCompatibility JavaVersion.VERSION_21`，
必须用 JDK 21。用 `java -version` 确认，并检查 `JAVA_HOME` 指向的是 21 而不是 17。
</details>

## 六、发布到 GitHub

**已经发布好了**：<https://github.com/mengxiangbaofu888/electro-tutor>
（想知道现在有多少提交和标签：`git rev-list --count HEAD` 数提交，`(git tag).Count` 数标签。
这里故意不写死数字——写死的数字一定会腐烂。）

这一节留下来，是为了**以后发新版本**时照着做。

### 🔒 发布铁律：只增不改（用户明确要求）

**已经推上去的东西一律不动。** 具体来说，永远不要做这些事：

| ❌ 不许做 | ✅ 应该做 |
|---|---|
| `git commit --amend` 改已推送的提交 | 新起一个提交 |
| `git push --force` / `--force-with-lease` | 普通 `git push`（历史只往前走） |
| 删除或重建已推送的标签（`git tag -d` + 重新 `git tag`） | **新版本用新标签**（v0.26.1、v0.27.0…） |
| 改已发布 Release 的内容 / 覆盖它的 APK | 发一个新 Release |

原因很实际：**老版本要能一直回滚。** 用户手机里装的可能是 v0.25.3，
它必须永远能从 GitHub 上原样下回来。改写历史会让"下载到的 v0.25.3"
和当时的不一样，等于把回滚这条路悄悄毁掉。

判断方法：这个提交/标签**推上去过吗**？

- 没推过 → 随便整理（改消息、squash、删标签重建都没事）；
- 推过了 → 只能往后加。

自查命令（本地每个标签的哈希 vs 远端，应当全部一致）：

```bash
git ls-remote --tags origin          # 或到仓库 Releases / Tags 页面看一眼
```

> 本项目至今遵守得很好：发布后新增的都是新提交 + 新标签，
> v0.25.3 与 v0.26.0 两个 Release 并存，互不影响。

### 发新版本：打标签 → 自动出包 → 自动挂 Release

日常发版只需要两步：

```bash
git tag -a v0.26.0 -m "v0.26.0 说明"
git push origin v0.26.0
```

> 📌 纯文档/说明的修正不一定要发新版本：直接提交推到 `main` 就是**新增提交**，
> 同样不动任何已有标签和 Release。要不要给文档也打个标签，看你自己。

推上去之后 GitHub Actions 会自动：装工具链 → 跑类型检查 → 跑单元测试 →
构建网页产物 → 打包 APK → **把 APK 挂到该标签的 Release 上**。
大概 2.5 分钟出结果（实测 148~182 秒），Release 页面就能直接下载安装包。

> ⚠️ 推**多个标签**时也是一样，每个 `v*` 标签都会各触发一次构建。
> 所以别为了图省事一次推一堆标签，会白白跑很多次。

### 首次发布（已完成，留作记录）

$env:GITHUB_TOKEN = "ghp_xxxxxxxx"            # 勾选 repo + workflow 权限

### 如果 GitHub 连不上

国内直连 GitHub 常被重置（`github.com` 与 `raw.githubusercontent.com` 会断，
但 `api.github.com` 有时能通；而且**时好时坏**——同一台机器上，
半小时前推得动、半小时后就报
`Failed to connect to github.com port 443 ... Could not connect to server`）。
这时改用本地代理。

**第一步：代理软件在运行吗？** 用一条命令看谁在监听（不用猜端口）：

```powershell
Get-NetTCPConnection -State Listen |
  Where-Object { $_.LocalPort -in 7890,7891,7897,1080,10808 } |
  ForEach-Object { "$($_.LocalPort) → $((Get-Process -Id $_.OwningProcess).ProcessName)" }
```

本项目实测输出是 `7890 → mihomo`（mihomo 是 Clash 的内核）。
各家默认端口不一样：旧版 Clash for Windows 常见 `7890`，
Clash Nyanpasu / Verge Rev 也可能是 `7897`——**以实际监听的那个为准**。

> ⚠️ 注意：`Get-NetTCPConnection` 查的是"真的有人监听"，比注册表里的
> 「系统代理」设置**可靠得多**。本项目踩过一次：
> 注册表写着 `127.0.0.1:7897`，但 7897 根本没人在听（那是上一次退出时留下的残值），
> 实际在跑的是 7890。结果浏览器把所有网站都打不开，
> 而 `git` 加 `GITHUB_PROXY=http://127.0.0.1:7890` 反而能推。

**⚠️ 不要用 `git config --global http.proxy` 把代理写死。**
那是**永久**配置：哪天代理软件没开，git 会一直报
`Failed to connect to 127.0.0.1 port <端口>: 拒绝连接`，
而且你多半想不起来是自己设过它——浏览器遇到同款问题的表现就是"所有网站都打不开"。

正确做法是**只在这一次命令上临时带代理**，用完即弃：

```bash
git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push -u origin main
```

`scripts/publish-github.mjs` 就是这么干的——它只看 `GITHUB_PROXY` 环境变量，不碰你的全局配置。

如果报 `schannel: AcquireCredentialsHandle failed` 或 `Recv failure`，那是 Windows 的 TLS 后端问题，
换成 OpenSSL 后端（同样建议只在单次命令上加 `-c http.sslBackend=openssl`；脚本已自动带上）：

```bash
git config --global http.sslBackend openssl
```

**如果你已经写死了全局代理**，想取消：

```bash
git config --global --unset http.proxy
git config --global --unset https.proxy
```

顺手一条自查命令——列出所有 git 配置里和代理有关的项，**正常应该什么都不输出**：

```bash
git config --list --show-origin | findstr /i proxy
```

## 七、常见问题

<details>
<summary><b>打包 APK 报 <code>Your project path contains non-ASCII characters</code></b></summary>

**项目路径里不能有中文（或其他非 ASCII 字符），这是安卓构建工具自己的硬限制。**
只要路径里出现一个中文字符，AGP 会在配置阶段直接失败：

```
> Failed to apply plugin 'com.android.internal.application'.
   > Your project path contains non-ASCII characters. This will most likely
     cause the build to fail on Windows. Please move your project to a different directory.
```

注意它检查的是**整个绝对路径**——不只是项目文件夹的名字。
`D:\我的项目\electro-tutor\` 一样会失败，因为祖先目录里有中文。

有两条路，本项目**两条都走过**，结论如下：

**路线 A（默认，最稳）：把项目放到纯英文路径下。**
改路径是成本最低、最不容易出事的做法。

**路线 B（本项目实际采用）：打开官方的开关，允许中文路径。**
在 `android/gradle.properties` 里加一行：

```properties
android.overridePathCheck=true
```

本项目就是这么用的——文件夹名是中文的 `D:\github\电工PLC陪练-2026.10\electro-tutor\`，
并且**实测能正常出包**：Gradle `BUILD SUCCESSFUL`，
产物用 `aapt2 dump badging` 能正常解析（包名 `com.electrotutor.app`、
应用名「电工陪练」、minSdk 24 / targetSdk 36），
`apksigner verify` 显示已用 Android Debug 证书签名，可以正常安装。

⚠️ **但这条路有代价，官方原话是"most likely cause the build to fail"：**
- 它绕过的是一个真实存在的兼容性问题，风险主要在**资源合并 / aapt2 / 打包含中文的中间产物**上；
- 本机现在是好的，但升级 AGP、build-tools 或依赖后，可能以很难查的方式炸掉；
- **万一哪天打包突然报奇怪的错（找不到文件、资源合并失败、aapt2 崩溃），
  第一件该做的事就是把文件夹改成纯英文名再试一次**——这比读报错快得多。

两条路的共同前提：中文路径下 `npm run dev`、`npm test`、网页版都正常，
**只有打包 APK（走 Gradle）受影响**。所以路径带中文时前面全都能跑通，
到打包才失败，很容易误以为是别的问题。

> 另外 `android/local.properties` 里的 SDK 路径要写成 `\uXXXX` 转义
> （例如 `\u7535\u5de5` 就是"电工"），因为 Java 的 `.properties` 默认按
> ISO-8859-1 解码，直接写中文会变成乱码、导致找不到 SDK。
</details>

<details>
<summary><b>GitHub Actions 打包失败：<code>Failed to find package 'tools'</code></b></summary>

这是 `android-actions/setup-android@v3` 自己的问题，**跟你的项目代码无关**。
它在"准备 Android SDK"这一步内部会执行 `sdkmanager tools`，
而 Google 已经下架了遗留的 `tools` 包，所以 v3 必然失败：

```
[command]/usr/local/lib/android/sdk/cmdline-tools/16.0/bin/sdkmanager tools
Warning: Failed to find package 'tools'
Error: The process 'sdkmanager' failed with exit code 1
```

**解决办法**：升级到 `v4`，并显式指定要装的包：

```yaml
      - name: 准备 Android SDK
        uses: android-actions/setup-android@v4
        with:
          packages: 'platform-tools'
```

上传到 GitHub 之前，这个工作流**从来没有真正跑过**——本地 `npm run apk` 能出包，
会让人误以为 CI 也是好的。这类"从没被执行过的配置"只能靠真跑一次来验证。
</details>

<details>
<summary><b>构建时报 <code>spawn EPERM</code>（Vite 执行 net use 探测网络驱动器）</b></summary>

Vite 在 Windows 上会执行 `net use` 并用管道读取输出，用来判断项目是否在网络驱动器上。某些受限环境（沙箱 / 严格安全策略）禁止子进程管道，就会抛 EPERM。

解决办法：在**普通终端**里运行构建（不要用受限沙箱），或者改用 WSL。
</details>
